## Answer

Use **policy-scoped Approval Request review** as the owner management experience.

1. The authenticated owner first selects one Restricted Group Policy. The selector lists every policy, with policies that have pending Approval Requests first and policies with no pending request after them.
2. The selected policy owns its own Approval Request queue; requests from different policies never mix. Within that queue, requests closest to deadline or expiry come first, followed by non-expiring requests from oldest to newest.
3. Queue rows show a short summary. The local TUI reveals the type-specific exact decision payload, normalized target scope, Capability Effects, Implementation Fingerprint, and Owner Decision controls only after the owner opens the request.
4. The local TUI and the exact Control Channel expose the same reviewable canonical Approval Requests and Owner Decision controls. They are projections of one active-profile-local queue, not separate queues.
5. The main Control Channel receives one compact Teams notification card per Approval Request. **Open review thread** creates a dedicated Teams thread for that exact canonical request. The exact decision payload and Owner Decision controls appear in the thread, not in the main-channel notification.
6. The first valid authenticated-owner terminal decision still wins immutably. A terminal state auto-closes the dedicated Teams thread. The main Control Channel retains only the terminal result and an **Open audit record** link. If the same policy has another pending request, the next request opens automatically and receives a new compact notification and a new dedicated thread.
7. Policy status, Capability Grants, Persistent Denials, Production Activation Proposal, Activation Evidence Manifest, Owner Risk Exceptions, rollback, and audit history remain secondary views rather than competing with the Approval Request queue.
